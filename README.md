# Baraly API

FastAPI, PostgreSQL, SQLAlchemy 2 (async), Alembic, Poetry, Docker.

## Запуск в Docker

```bash
cp .env.example .env   # задайте POSTGRES_PASSWORD
make up
```

- API: http://localhost:8000
- Документация: http://localhost:8000/docs
- Проверка БД: http://localhost:8000/health/ready

Миграции применяются автоматически перед стартом API. Код из `app/` смонтирован в контейнер, сервер перезапускается при изменениях.

Если порт 8000 или 5432 занят, поменяйте `API_HOST_PORT` или `POSTGRES_HOST_PORT` в `.env`.

## Локальная разработка

Нужны Python 3.12 и Poetry 2.

```bash
make install
docker compose up -d db
make migrate
make run
```

## Пользователи и авторизация

Вход только через Google и Apple, паролей нет.

1. Фронтенд получает `id_token` через Google Identity Services или Sign in with Apple.
2. Отправляет его на `POST /api/v1/auth/google` или `POST /api/v1/auth/apple`.
3. API проверяет подпись, `iss`, `aud`, `exp` и возвращает `access_token` и `refresh_token`.

Apple сообщает имя только клиенту и только при первом входе, поэтому фронтенд передаёт `first_name` и `last_name` в запросе. Для Apple нужно запрашивать scope `email`.

| Запрос | Что делает |
| --- | --- |
| `POST /api/v1/auth/google` | вход через Google |
| `POST /api/v1/auth/apple` | вход через Apple |
| `POST /api/v1/auth/refresh` | новая пара токенов, старый refresh-токен отзывается |
| `POST /api/v1/auth/logout` | выход, отзыв refresh-токена |
| `GET /api/v1/users/me` | профиль |
| `PATCH /api/v1/users/me` | изменение имени, фамилии и телефона |

Для работы входа укажите `GOOGLE_CLIENT_IDS` и `APPLE_CLIENT_IDS` в `.env`. Пока списки пусты, вход через провайдера возвращает 401.

### Таблицы

| Таблица | Ключ | Поля |
| --- | --- | --- |
| `users` | `id` | `email` (unique), `first_name`, `last_name`, `phone`, `avatar_url`, `is_active`, `created_at`, `updated_at` |
| `auth_identities` | `provider`, `subject` | `user_id` → `users`, `created_at`; unique (`user_id`, `provider`) |
| `refresh_tokens` | `id` | `user_id` → `users`, `token_hash` (unique), `expires_at`, `revoked_at`, `created_at` |

- Аккаунты Google и Apple с одним подтверждённым email объединяются в одного пользователя.
- Email приходит от провайдера и через API не меняется: иначе можно было бы вписать чужой адрес и получить доступ к чужому аккаунту при объединении.
- Телефон не подтверждается, поэтому не уникален.
- При скрытом email Apple создаётся отдельный пользователь, так как адрес не совпадает.

## Туры

Публичные запросы:

| Запрос | Что делает |
| --- | --- |
| `GET /api/v1/tours` | каталог с фильтрами, сортировкой и пагинацией |
| `GET /api/v1/tours/{id}` | страница тура |
| `GET /api/v1/tours/{id}/reviews` | отзывы о туре |
| `GET /api/v1/tours/{id}/reviews/photos` | все фото из отзывов о туре |
| `GET /api/v1/tours/{id}/departures` | календарь: даты выездов с ценой и числом мест, `date_from`/`date_to`, по умолчанию год вперёд |
| `GET /api/v1/tour-operators`, `/{id}`, `/{id}/tours`, `/{id}/reviews` | операторы, их туры и отзывы |
| `GET /api/v1/tags`, `/languages`, `/locations` | значения для фильтров |

Фильтры `GET /api/v1/tours`: `q`, `location`, `date_from`, `date_to`, `persons`, `duration_min`, `duration_max`, `price_min`, `price_max`, `age_from`, `age_to`, `tags`, `languages`, `activity`. Несколько значений передаются повтором параметра: `?tags=water&tags=ethno`. Сортировка `sort`: `popular`, `rating`, `price_asc`, `price_desc`, `newest`. Страницы: `limit` (до 100) и `offset`.

Запросы с токеном пользователя:

| Запрос | Что делает |
| --- | --- |
| `PUT`, `DELETE /api/v1/tours/{id}/reviews/me` | свой отзыв о туре: один на тур, повторный `PUT` изменяет его |
| `PUT`, `DELETE /api/v1/tour-operators/{id}/reviews/me` | свой отзыв о компании |
| `GET /api/v1/users/me/reviews` | мои отзывы |
| `POST /api/v1/users/me/images` | загрузка фото для отзыва, ссылка идёт в `photo_urls` (до 10, только к отзывам о турах) |
| `POST`, `DELETE /api/v1/users/me/avatar` | загрузить или убрать свой аватар |
| `GET /api/v1/users/me/favorites` | избранные туры |
| `GET /api/v1/users/me/favorites/ids` | идентификаторы избранных туров для отметок в каталоге |
| `PUT`, `DELETE /api/v1/users/me/favorites/{tour_id}` | добавить или убрать из избранного |

Запросы администратора:

| Запрос | Что делает |
| --- | --- |
| `GET`, `POST /api/v1/admin/tours` | все туры, включая черновики; создание |
| `GET`, `PUT`, `DELETE /api/v1/admin/tours/{id}` | один тур; `PUT` заменяет его содержимое целиком |
| `GET`, `POST /api/v1/admin/tour-operators` | список компаний с фильтрами и счётчиками; создание, можно сразу с `owner_email` |
| `GET`, `PUT`, `DELETE /api/v1/admin/tour-operators/{id}` | компания |
| `PATCH /api/v1/admin/tour-operators/{id}/status` | отключить или включить компанию |
| `PATCH /api/v1/admin/tours/{id}/moderation` | скрыть тур с причиной или вернуть |
| `POST`, `DELETE /api/v1/admin/tags`, `/admin/locations` | справочники |
| `GET /api/v1/admin/reviews` | все отзывы: фильтры `kind`, `operator_id`, `tour_id`, `user_id`, `rating_min`, `rating_max`, `is_hidden`, `q`, `sort` |
| `GET`, `PATCH`, `DELETE /api/v1/admin/reviews/{id}` | отзыв: скрыть, вернуть, удалить |

Фильтры `GET /api/v1/admin/tours`: всё из каталога, плюс `operator_id`, `is_published`, `is_blocked`. Фильтры `GET /api/v1/admin/tour-operators`: `q`, `is_active`, `sort` (`name`, `newest`, `rating`, `tours`).

Первого администратора создаёт команда (пароль вводится скрыто, в `.env` не хранится):

```bash
make create-admin email=you@example.com
# или в Docker
docker compose exec api python -m app.cli create-admin you@example.com
```

| --- | --- | --- |
| `tour_operators` | `id` | название, контакты, логотип |
| `tours` | `id` | описание, цена в USD, длительность, активность, комфорт, возраст, условия |
| `tags`, `tour_tags` | `slug`; `tour_id`, `tag_slug` | типы туров, связь многие ко многим |
| `languages`, `tour_languages` | `code`; `tour_id`, `language_code` | языки, связь многие ко многим |
| `locations` | `id` | название и координаты |
| `tour_images` | `tour_id`, `position` | фотографии, первая является обложкой |
| `tour_inclusions` | `tour_id`, `is_included`, `position` | что включено и не включено |
| `tour_days` | `id`; unique (`tour_id`, `day_number`) | программа по дням |
| `tour_day_meals` | `day_id`, `meal` | питание в день |
| `tour_day_landmarks` | `day_id`, `position` | места в программе дня |
| `tour_day_images` | `day_id`, `position` | фото мест дня |
| `tour_departures` | `id` | даты выезда, число мест, своя цена |
| `tour_review_photos` | `review_id`, `position` | фото в отзыве о туре |
| `tour_reviews` | `id`; unique (`tour_id`, `user_id`) | оценка и текст |
| `favorites` | `user_id`, `tour_id` | избранное |

- Рейтинг и число отзывов тура и оператора не хранятся, а считаются из `tour_reviews`, поэтому не расходятся с отзывами.
- У тура без точных дат заполняется `schedule_note` (например, `Any day`). Такой тур подходит под любой фильтр по датам и числу человек.
- Идентификаторы выездов не меняются при `PUT`, если передавать `id` существующего выезда.
- У выезда может быть своя цена (`price`), иначе действует цена тура. В ответах у выезда всегда итоговая цена за человека.
- У каждого дня программы есть фото мест (`image_urls`), у тура есть `duration_nights` и подзаголовок `short_description`.
- В отзыве можно прикрепить только свои фото, загруженные через `POST /users/me/images`: чужие ссылки отклоняются.

## Кабинет компании

Компанию создаёт администратор платформы и приглашает владельца по email. Приглашённый входит через Google или Apple и получает доступ: сразу, если уже зарегистрирован, иначе при первом входе. Список своих компаний: `GET /api/v1/users/me/companies`.

| Роль | Что может |
| --- | --- |
| `owner` | профиль компании, сотрудники и приглашения, туры, картинки |
| `manager` | туры, картинки, локации |

Последнего владельца нельзя понизить или удалить. Администратор платформы проходит любые проверки кабинета, поэтому через эти же запросы может добавлять туры и сотрудников в конкретную компанию.

| Запрос | Что делает |
| --- | --- |
| `GET`, `PUT /api/v1/company/{id}` | профиль компании |
| `GET`, `POST /api/v1/company/{id}/members` | сотрудники; приглашение по email и роли |
| `PATCH`, `DELETE /api/v1/company/{id}/members/{user_id}` | смена роли, удаление |
| `GET`, `DELETE /api/v1/company/{id}/invitations` | ожидающие приглашения |
| `GET`, `POST /api/v1/company/{id}/tours` | туры компании, включая черновики и скрытые админом |
| `GET`, `PUT`, `DELETE /api/v1/company/{id}/tours/{tour_id}` | один тур |
| `POST /api/v1/company/{id}/images` | загрузка JPEG, PNG или WebP, ответ содержит URL для `image_urls` |
| `POST /api/v1/company/{id}/locations` | новая локация в общем справочнике |
| `GET /api/v1/company/{id}/reviews` | отзывы о компании и её турах, включая скрытые |

- Тур, скрытый админом, компания не может показать снова: `is_blocked` и `blocked_reason` меняет только админ.
- Отключённая компания пропадает с сайта вместе с турами, а её сотрудники теряют доступ к кабинету.
- Рейтинг компании считается из видимых отзывов о ней и о её турах.

## Картинки и MinIO

Картинки хранятся в MinIO, бакет `baraly` создаётся при первой загрузке и открыт только на чтение файлов (список файлов закрыт). Консоль MinIO: http://localhost:9001, логин и пароль: `S3_ACCESS_KEY` и `S3_SECRET_KEY`. Формат проверяется по содержимому файла, размер ограничен `MAX_IMAGE_SIZE_MB`.

Официальные Docker-образы MinIO больше не публикуются в Docker Hub и quay.io, поэтому `docker-compose.yml` использует уже скачанный образ `minio/minio:latest` (`pull_policy: never`). На новой машине образ нужно собрать или подставить другое S3-совместимое хранилище: код работает с любым S3 через `S3_ENDPOINT`. Для продакшена задайте `S3_PUBLIC_URL` (домен или CDN) и отдельные ключи доступа вместо root-пользователя.

## Роли и модерация

| Роль | Доступ |
| --- | --- |
| `user` | сайт, профиль, отзывы, избранное, кабинет своей компании |
| `moderator` | все туры в админке, одобрение и отклонение, скрытие туров |
| `admin` | всё: компании, проверка компаний, пользователи и роли, отзывы, справочники |

По почте и паролю (`POST /api/v1/auth/login`) входят админы, модераторы и сотрудники компаний. Путешественники входят через Google и Apple.

Пароль сотруднику компании задаётся при создании аккаунта: админ указывает `owner_password` при создании компании, владелец передаёт `password` при добавлении сотрудника (`POST /api/v1/company/{id}/members`). Пароль можно задать только новой почте: на существующий аккаунт пароль не ставится, иначе владелец компании мог бы захватить чужой аккаунт. Админ может сбросить пароль сотруднику платформы или компании.

- `POST /api/v1/admin/staff` — создать модератора или админа с паролем (или сделать сотрудником существующего пользователя);
- `PUT /api/v1/admin/users/{id}/password` — задать сотруднику новый пароль, это снимает блокировку и закрывает его сессии;
- `POST /api/v1/users/me/password` — сменить свой пароль, после этого все сессии закрываются;
- `PATCH /api/v1/admin/users/{id}/role` — сменить роль; бывший сотрудник теряет пароль от админки;
- `GET /api/v1/admin/users?q=&role=` — список пользователей.

Пароли хранятся как хеш Argon2, нужно не меньше 10 символов с буквами и цифрами. После 5 неверных паролей подряд вход блокируется на 15 минут. Ответ одинаковый для неизвестного email и неверного пароля. Свою роль админ поменять не может.

Проверка компании: `PATCH /api/v1/admin/tour-operators/{id}/verification` с `is_verified` и `note` (какую проверку прошла компания). Публичная страница компании показывает `is_verified`.

| Кто сохраняет тур | Статус модерации |
| --- | --- |
| проверенная компания | `approved`, тур сразу на сайте |
| непроверенная компания | `pending`, после каждого изменения тур снова ждёт проверки |
| админ или модератор | `approved` |

Очередь модерации: `GET /api/v1/admin/tours?moderation_status=pending`. Решение: `PATCH /api/v1/admin/tours/{id}/approval` со `status` `approved` или `rejected`; при отклонении нужен `comment`, его видит компания. Скрыть одобренный тур: `PATCH /api/v1/admin/tours/{id}/moderation`.

На сайте тур виден, если он опубликован, одобрен, не скрыт и компания активна.

### Прошедшие туры

Тур, у которого были даты и все они прошли, автоматически пропадает из каталога: проверка идёт в каждом запросе, задания по расписанию не нужны. Туры без точных дат (`schedule_note`) не устаревают. Страница прошедшего тура открывается по ссылке с `is_expired: true`, на неё можно оставить отзыв, и тур остаётся в избранном. Компания возвращает тур в каталог, добавив новую дату. Фильтр `is_expired` есть в админке и в кабинете компании.

## Бронирование

1. `POST /api/v1/bookings` с `departure_id` и списком путешественников (первый — контактное лицо, у него нужен телефон или email). Места удерживаются на `BOOKING_HOLD_MINUTES` (15 минут), остальные сразу видят меньше свободных мест.
2. `POST /api/v1/bookings/{id}/pay` возвращает `redirect_url` страницы оплаты. Онлайн платится предоплата тура (`prepayment_percent`), остальное организатору. При предоплате 0% бронь подтверждается сразу.
3. Провайдер сообщает об оплате, бронь становится `confirmed` и видна в `GET /users/me/bookings`, в кабинете компании (`GET /company/{id}/bookings`) и у админа (`GET /admin/bookings`).
4. Не оплатил вовремя или нажал `POST /bookings/{id}/cancel` — места возвращаются. Задание по расписанию не нужно: просроченное удержание просто перестаёт учитываться, а бронь показывается как `expired`.

Защита от перепродажи:

- при бронировании строка выезда блокируется (`SELECT ... FOR UPDATE`), брони на одну дату идут по очереди; тест `test_booking_concurrency.py` запускает 10 одновременных покупок на 3 места и проверяет, что продано ровно 3;
- повторное нажатие «Купить» заменяет прежнее удержание этого пользователя на ту же дату, а не копит места;
- оплата после окончания удержания подтверждается, только если места ещё есть, иначе бронь `expired` и платёж нужно вернуть;
- компания не может уменьшить вместимость ниже проданных мест, удалить дату с бронями или удалить тур с бронями.

Свободные места выезда: `seats_left` в календаре и в карточке тура; фильтр каталога `persons` учитывает занятые места. Возраст путешественников проверяется по возрастным ограничениям тура на дату начала.

Сейчас подключён тестовый провайдер `PAYMENT_PROVIDER=fake`: оплата завершается вызовом `POST /api/v1/payments/fake/{reference}/complete`, деньги не списываются. В production он запрещён настройками. Для реальной оплаты нужно реализовать `PaymentGateway` для выбранного провайдера и вебхук, который вызывает `ConfirmPayment`.

| `bookings` | `id` | пользователь, выезд, число мест, цены на момент брони, статус, срок удержания, платёж |
| `booking_travelers` | `booking_id`, `position` | имя, фамилия, дата рождения, пол, телефон, email |

## Архитектура

Зависимости направлены только внутрь: `presentation` и `infrastructure` → `application` → `domain`.

```
app/
├── domain/            сущности и бизнес-правила, без внешних библиотек
├── application/
│   ├── ports/         интерфейсы (Protocol), которые нужны сценариям
│   └── use_cases/     сценарии, работают только через порты
├── infrastructure/    реализации портов: БД, внешние сервисы
├── presentation/api/  роуты, схемы, сборка зависимостей
├── config.py          настройки из окружения
└── main.py            создание приложения
```

### Как добавить новую функцию

1. Сущность и её правила в `domain/`.
2. Интерфейс репозитория в `application/ports/`.
3. Сценарий в `application/use_cases/`.
4. ORM-модель и репозиторий в `infrastructure/`. Импортируйте модуль модели в `migrations/env.py`, затем выполните `make migration`.
5. Сборка сценария в `presentation/api/dependencies.py`.
6. Роут в `presentation/api/v1/` и подключение в `v1/router.py`.

Пример сквозного прохода через слои: `GET /health/ready`.
